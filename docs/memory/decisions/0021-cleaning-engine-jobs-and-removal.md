# 0021 Cleaning engine: daemon jobs, id-addressed removal, one guard, one elevated helper

## Context and Problem Statement
oh-my-clear needs every cleaning area (system/browser/developer junk, trash, installers, leftovers, space lens, large/old files, duplicates), a complete uninstaller for macOS/Windows/Linux (registry on Windows; Full Disk Access, App Management and admin rights on macOS) and startup-item management. Scans take seconds to minutes, must be fast with low memory, and removal must never touch anything the user did not see in a report.

## Considered Options
* Scanning in the UI process — rejected by ADR 0008 (UI never does filesystem work)
* One request per scan with a long timeout — rejected: 10 s client timeout, no progress, no cancel
* **Daemon jobs**: `start_job` → pushed `job` events (lossy progress) → `job_result` → `release_job` (**chosen**)
* Removal by client-supplied paths vs **removal by item ids of a retained scan** (**chosen**)

## Decision Outcome
- **Crates** (`LAYERS`): `omc-scan` (walker, junk catalogues, space lens, large/old, duplicates, deletion, guard; deps omc-proto) and `omc-apps` (per-OS app inventory, related files/registry, uninstall, leftovers, startup items, removal executor, elevation; deps omc-proto + omc-scan). Platform code lives in `omc-apps/src/{macos,windows,linux}/` behind one `pub(crate)` function set. omc-engine routes jobs; the UI only speaks omc-proto.
- **Wire** (`PROTOCOL` 2): `JobSpec` / `JobOutput` / `JobUpdate` (`Event::Job`), `SystemInfo`, `Get/PutSettings`, `SpaceChildren` for drill-down. Reports carry enums (kinds, tags, reasons) that the UI localises; names/paths are raw.
- **Walker**: one rayon pool per job (`scan_threads`, 0 = all CPUs — speed first), one task per directory, visitors aggregate (nothing collects all paths), never follows symlinks/junctions, one-file-system with the macOS data-volume firmlink special case, cloud placeholders count 0 bytes and are never read. Space lens keeps directory nodes (keyed by XXH3 of the path, names in one buffer) plus up to 32 files ≥ 64 KiB per directory (the rest aggregated into one `rest` node); duplicates = size → 16 KiB head/tail XXH3-128 → full XXH3-128.
- **Removal**: every scan returns `Scanned { report, targets }`; `clean`/`uninstall` reference item ids of a retained job of the same epoch, so no path ever comes from the client. `omc_scan::Guard` refuses roots, home, standard container folders, OS trees and user exclusions on every path (also in the elevated helper). Junk defaults to permanent deletion, user files/apps to the Trash (`trash` crate, `NsFileManager` on macOS: no Finder automation prompt); Trash never silently falls back to permanent deletion.
- **Elevation**: items needing admin (and permission failures) go to ONE `oh-my-clear-daemon elevated <manifest>` run per clean: macOS `osascript … with administrator privileges`, Windows `Start-Process -Verb RunAs`, Linux `pkexec`. The manifest lives in a private 0700 temp dir; the helper re-applies the guard.
- **Settings** are daemon-owned (`settings.toml` in the config dir, `CleanSettings` + an opaque `ui` string map for UI prefs) so jobs read them directly and future tray/scheduled work sees the same values; `SettingsChanged` is pushed on every write.
- **Safety defaults**: only `Safety::Safe` items (regenerated by the OS/app) are preselected; cookies/history/site data/sessions are opt-in; caches of running apps are flagged and not preselected; temp files/logs younger than `junk_min_age_hours` survive; leftover matches carry a confidence and only those ≥ the setting are preselected; Windows registry keys are exported to `.reg` before deletion (setting, default on).

### Consequences
* Good, because progress/cancel work for every long operation, removal is auditable (only reported items), one admin prompt covers a whole clean, and platform code is isolated per OS.
* Bad, because job outputs live in daemon memory until released (capped at 64 finished jobs) and a daemon restart invalidates every result (the UI rescans).
* Bad, because Windows/Linux platform code is only compile-checked on the macOS development host; their pure parsers carry tests that run on those OSes' CI.
