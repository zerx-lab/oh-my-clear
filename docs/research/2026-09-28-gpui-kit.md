## 1. What gpui-kit is, crates, versions, toolchain, system deps

### Identity
- **GPUI Kit** = Longbridge's Rust desktop framework on top of Zed's GPUI. Repo `https://github.com/longbridge/gpui-kit` (this is the former `longbridge/gpui-component` repo, created 2024-06-13; the `gpui-component` crate's repository field now points here). Site/docs: `https://gpui-kit.com`, per-page Markdown via `https://gpui-kit.com/<path>.md` (e.g. `/component/dock.md`).
- Five layers (llms-full "GPUI Kit" /docs):
  - `gpui` — UI runtime (published as **`gpui-pre`**, see below)
  - `gpui-kit` — umbrella entry crate; re-exports GPUI (`use gpui_kit::*;`) + `gpui_kit::component`, `gpui_kit::base`, `gpui_kit::assets`, `gpui_kit::platform`
  - `gpui-base` — unstyled behavior: focus, overlays, virtual lists, dock model, Root, motion, TextView (canonical), plot
  - `gpui-component` — styled library, 75+ components, themes, DataTable, Dock, code Editor
  - `gpui-shell` — optional JS (QuickJS) extension host; NOT pulled by `gpui-kit`
- Docs rule (verbatim, /docs/installation): "It brings in matching GPUI crates, so an application using this setup does not need to list GPUI separately." Repo skill: "**One dependency.** Applications depend on `gpui-kit` alone."

## 2. Minimal app skeleton

### Verbatim from docs (/docs/getting-started and /docs "Quick Example")
```rust
use gpui_kit::component::button::{Button, ButtonVariants};
use gpui_kit::*;

struct HelloWorld;

impl Render for HelloWorld {
    fn render(&mut self, _: &mut Window, _: &mut Context<Self>) -> impl IntoElement {
        div()
            .flex()
            .flex_col()
            .size_full()
            .items_center()
            .justify_center()
            .gap_2()
            .child("Hello, World!")
            .child(
                Button::new("hello")
                    .primary()
                    .label("Click me")
                    .on_click(|_, _, _| println!("Clicked!")),
            )
    }
}

fn main() {
    application()
        .with_assets(assets::Assets)
        .run(|cx| {
            init(cx);

            open_window(WindowOptions::default(), cx, |_, cx| {
                cx.new(|_| HelloWorld)
            })
            .expect("Failed to open window");
        });
}
```
Startup sequence (verbatim): "1. `gpui_kit::application()` creates the desktop application; `.with_assets(...)` registers the default icon source. 2. `gpui_kit::init(cx)` initializes the enabled Kit layers, including component themes. Call it once before opening application windows or constructing components. 3. `gpui_kit::open_window(...)` creates an `Entity<HelloWorld>` from the closure and wraps it in a `Root`. `Root` owns the window's overlay layers, including dialogs, sheets and notifications. Return your content view from the closure, not another `Root`."

`open_window` signature (crates/kit/src/lib.rs):
```rust
pub fn open_window<V: Render>(
    options: WindowOptions,
    cx: &mut App,
    build: impl FnOnce(&mut Window, &mut App) -> Entity<V>,
) -> Result<(AnyWindowHandle, Entity<V>)>
```
"In an async context, call this inside `cx.update`." Root docs: "Applications define their own quit and close-window actions and key bindings. `gpui_kit::init` does not install them."

### Theme
`init(cx)` installs the component theme. Access: `use gpui_kit::component::ActiveTheme as _;` → `cx.theme().background / .foreground / .primary / .border / .muted`. Theme JSON registry (verbatim /component/theme):
```rs
use std::path::PathBuf;
use gpui_kit::{App, SharedString};
use gpui_kit::component::{Theme, ThemeRegistry};

pub fn init(cx: &mut App) {
    let theme_name = SharedString::from("Ayu Light");
    // Load and watch themes from ./themes directory
    if let Err(err) = ThemeRegistry::watch_dir(PathBuf::from("./themes"), cx, move |cx| {
        if let Some(theme) = ThemeRegistry::global(cx)
            .themes()
            .get(&theme_name)
            .cloned()
        {
            Theme::update(cx, |current| current.apply_config(&theme));
        }
    }) {
        tracing::error!("Failed to watch themes directory: {}", err);
    }
}
```
20+ themes in repo `themes/`.

### No-panic rewrite (compiled + clippy-clean + ran in `/tmp/gkprobe/src/main.rs`)

```rust
fn bind_keys(cx: &mut App) -> Result<()> {
    let ctx = Some(Rc::new(KeyBindingContextPredicate::parse("Workspace")?));
    let send = KeyBinding::load("secondary-enter", Box::new(SendMessage), ctx, false, None, &DummyKeyboardMapper)?;
    let quit = KeyBinding::load("secondary-q", Box::new(Quit), None, false, None, &DummyKeyboardMapper)?;

```

## 3. Core patterns

### Entity / Context / Render
- `Entity<T>` = handle to app-owned state; `cx.new(|cx| T)`; `entity.read(cx) -> &T`; `entity.read_with(cx, |t, cx| ..)`; `entity.update(cx, |t, cx| ..)`; `entity.downgrade() -> WeakEntity<T>` (whose `update` returns `Result`).
- A View = `Entity<T>` where `T: Render`; `fn render(&mut self, window: &mut Window, cx: &mut Context<Self>) -> impl IntoElement` rebuilds an element tree each frame. `RenderOnce` (+ `#[derive(IntoElement)]`) for stateless reusable components built from owned data.
- Contexts: `App` (global), `Context<T>` (derefs to App, for entity T), `Window`, `AsyncApp`, `AsyncWindowContext`, `TestAppContext`/`VisualTestContext`.
- `cx.notify()` marks the entity dirty → re-render. `cx.listener(|this, event, window, cx| ..)` adapts a method to an element callback.
- Architecture guidance (/docs/getting-started): "app shell → feature (model, commands, view) ├─ Entity<Model> retained state └─ Entity<View> retained view"; keep stateful children (e.g. `InputState`) as `Entity` fields created in `new`, never in `render`.

### State: observe / subscribe / EventEmitter / Global
```rust
impl EventEmitter<ChatEvent> for Chat {}
cx.emit(ChatEvent::MessageSent { total: self.sent });           // queued, delivered after update ends
let sub = cx.subscribe(&chat, |workspace, _chat, event, cx| { ...; cx.notify(); });
let sub = cx.subscribe_in(&input, window, |this, state, event: &InputEvent, window, cx| { .. });
cx.observe(&scroller, |_, _, cx| cx.notify()).detach();         // fires on target's cx.notify()
```
Store `Subscription`s in a `_subscriptions: Vec<Subscription>` field (dropping unsubscribes). `emit` does not request a render. Globals: `impl Global for T`, `cx.set_global`, `cx.try_global::<T>() -> Option<&T>` (use this; `cx.global::<T>()` panics if missing), `cx.update_global`, `cx.observe_global::<T>(..)`.

### Async: Task, spawn, background executor
Table (verbatim /docs/task):
| Start from | Runs on | Async callback receives | Use for |
|---|---|---|---|
| `cx.spawn(...)` in `Context<T>` | Foreground thread | `WeakEntity<T>`, `&mut AsyncApp` | Awaiting I/O, timers, then updating an Entity |
| `cx.spawn_in(window, ...)` | Foreground thread | `WeakEntity<T>`, `&mut AsyncWindowContext` | Work whose completion needs the same Window |
| `cx.spawn(...)` in `App` | Foreground thread | `&mut AsyncApp` | Application-level work without a current Entity |
| `cx.background_spawn(...)` | Background executor | No GPUI context | Expensive parsing or computation on owned `Send` data |

- `Task<T>`: **dropping cancels**. Store in a field (`Option<Task<()>>`, replace to cancel previous), await it, or `.detach()`. "Calling `cx.spawn(...);` as a bare statement drops the returned handle at the end of the statement and may cancel the task."
- Pattern (verbatim /docs/task "Move heavy work off the UI thread"):
```rust
self._parse_task = Some(cx.spawn(async move |this, cx| {
    let parsed = cx.background_spawn(async move {
        parse_document(source)
    }).await;

    _ = this.update(cx, |view, cx| {
        if view.revision != revision {
            return; // An older result must not replace newer content.
        }
        view.parsed = Some(parsed);
        cx.notify();
    });
}));
```
- Timers: `cx.background_executor().timer(Duration::from_millis(..)).await`. `FutureExt::with_timeout(dur, &executor)` exists in gpui.
- Rules: never start tasks unconditionally in `render`; no borrow of `self`/`cx` across `.await`; use request-id/revision guards; model idle/loading/loaded/failed explicitly; use bounded channels for streams (example uses unbounded only for demo).

## 4. Pitfalls (panics & async interplay)

### GPUI APIs that panic (verified in gpui-pre 0.3.7 source unless noted)
| API / situation | Panic | Avoid |
|---|---|---|
| `entity.update`/`read` on an entity already leased (same entity inside its own `update`/`render`/`listener`/`defer_in`, or indirect cycle A→B→A) | `entity_map.rs:232` `panic!("cannot {operation} {entity_type} while it is already being updated")` — also via `WeakEntity::update` (lease happens after upgrade) [INFERENCE for weak path] | Use the `&mut self` + inner `cx` given; never capture own `Entity` handle in its callbacks; flatten nested updates; in list delegates' `render_item` read from a plain snapshot field, not other entities; `cx.defer_in` then use the provided `&mut` |
| `KeyBinding::new(keys, action, ctx)` | `.unwrap()` on keystroke parse and context parse ("Panics on parse error.") | `KeyBinding::load(keys, Box::new(action), ctx.map(Rc::new), false, None, &DummyKeyboardMapper)?` + `KeyBindingContextPredicate::parse(ctx)?` (verified compiles) |
| `cx.global::<T>()`, `global_mut`, `update_global`, `remove_global` without installed value | panics (docs /docs/global) | `try_global`, `has_global`, `default_global`, `update_default_global` |
| Duplicate action name registration | panics at app creation (docs /docs/action) | unique namespace per `actions!` |
| `text_system().resolve_font` with no loadable fallback | panics (docs /docs/textsystem) | ship/register fonts before opening windows |
| Motion `with_damping`/`with_epsilon` invalid constants | panics (docs /base/motion) | `try_with_damping`, `try_with_epsilon` |
| `ReqwestClient::new()` (gpui-pre-reqwest-client) | `.expect("Failed to initialize HTTP client")` | `ReqwestClient::user_agent(..) -> anyhow::Result` / `proxy_and_user_agent` |
| `gpui_kit::open_window` internal `built.expect(..)` | library-internal, unreachable by construction | n/a (not our code) |
| Test helpers `window.find`, scoped `input` | panic by design in tests | fine in tests / use `try_find` |

Clippy note: the probe denied `unwrap_used, expect_used, panic, indexing_slicing` and `actions!`, `Render`, `cx.listener`, closures compiled clean — macro-expanded code from gpui did not trip the lints.

### Unwrap-heavy doc examples to rewrite
- Every doc `main`: `open_window(...).expect("Failed to open window")` → `if let Err(err) = … { log; cx.quit(); }`.
- `cx.bind_keys([KeyBinding::new(...)])` → `KeyBinding::load` (above).
- HTTP cache example: `LazyLock<tokio::runtime::Runtime>` built with `.expect("failed to start the HTTP runtime")`, `builder.headers_mut().unwrap()`, `CachedHttpClient::new(..).expect(..)` → build runtime fallibly at startup and store it in a `Global`/struct; `if let Some(h) = builder.headers_mut() { *h = … }`.
- VirtualList/stream examples index slices (`chars[current..current + chunk_size]`, `format!("Item {}", ix)` against `items[ix]`) → `.get(range)`/`.get(ix)`.
- MessageScroller example uses `.unwrap_or(...)` (fine) and `messages.get(index)` (already safe).
- `std::thread::sleep` in background/foreground examples is demo-only.

### Async runtime interplay
- GPUI has **its own executors**: foreground (UI thread, `!Send` ok) + background (platform dispatch queue / worker pool). It is not tokio. Docs, verbatim: "/// reqwest needs a tokio runtime; GPUI's executors are not one."
- **tokio can coexist** as a separate runtime. Two verified patterns:
  1. Official docs (/docs/image, HTTP cache): own `tokio::runtime::Builder::new_multi_thread().worker_threads(1).enable_all().build()` and from GPUI futures do `RUNTIME.spawn(request.send()).await??` — tokio's `JoinHandle` is executor-agnostic, so it can be awaited inside `cx.spawn`/`background_spawn`.
  2. Zed's own `gpui-pre-reqwest-client` (`ReqwestClient`): uses `tokio::runtime::Handle::try_current()` else a lazily-built static multi-thread runtime; implements `gpui::http_client::HttpClient`. Install with `cx.set_http_client(Arc::new(client))` (default native client "fails every request", so `img(url)` needs this).
  - gpui source (`app.rs`) comments that globals drop last "as this will also shutdown the tokio runtime" → Zed stores the runtime in a Global; do the same (own the `Runtime` in a `Global`, drop order after tasks).
- Streams into UI: spawn on tokio, send through a **bounded** `async-channel` (already in graph), receive in a stored `cx.spawn` task, `this.update(cx, ..)` + request-id guard + `cx.notify()`.
- Subprocesses: options — `smol::process`/`async-process` (already in graph, runtime-agnostic, awaitable directly in GPUI tasks) or `tokio::process` on the tokio runtime. [RECOMMENDATION, not from docs] Pick ONE I/O runtime: tokio (needed anyway for reqwest) and use `tokio::process` + `reqwest` there; GPUI executor strictly for UI/state; bridge with bounded channels / awaited `JoinHandle`s. Do not add a third runtime (async-std etc.). Note `smol` stays in the graph transitively regardless.
- HTTP client choice: [RECOMMENDATION] upstream `reqwest` (+ `tokio`) rather than `gpui-pre-reqwest` (a Zed fork published under Longbridge's snapshot, version-locked to gpui-pre; on desktop gpui-kit does not pull it). If the app also wants `img(url)` it must implement/adapt `gpui_kit::http_client::HttpClient` over its reqwest client (docs example shows exactly that adapter).
